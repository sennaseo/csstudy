# BackendQuest 기획서

> "처음 보는 사람도 게임처럼 클릭하고 맞추다 보면, 진짜 돌아가는 CRUD 백엔드 서비스 하나가 완성되는 실습형 백엔드 제작 게임"

본 문서는 비개발자 창업자도 그대로 이해할 수 있도록 쉽게 쓰되, 개발자가 바로 구현에 들어갈 수 있을 만큼 구체적으로 작성했습니다. 첫 트랙은 **Spring Boot**, 첫 완성 프로젝트는 **게시판 CRUD**를 기준으로 합니다.

---

## 1. 서비스 한 줄 소개

**BackendQuest** — 이론 강의 대신, 듀오링고처럼 짧은 게임 문제를 풀다 보면 실제로 작동하는 게시판 백엔드 서비스를 직접 완성하게 되는 실습형 백엔드 학습 게임.

부제: *"강의를 듣는 게 아니라, 백엔드를 조립한다."*

---

## 2. 핵심 사용자 페르소나

**메인 페르소나 — "도전하는 비전공자 지우" (24세)**
- 마케터/기획자/디자이너 등 비개발 직군이거나 취업 준비생.
- "코딩 배워야지" 하고 인강을 3번 결제했지만 매번 "변수, 자료형, 객체지향" 챕터에서 멈췄다.
- 원하는 것: *개념*이 아니라 *결과물*. "내가 만든 게시판이 인터넷에 떠 있다"는 경험.
- 좌절 포인트: 코드가 여러 파일에 흩어져 있고, 어떤 파일이 어떤 파일과 연결되는지 감이 안 온다.

**서브 페르소나 1 — "방향을 못 잡는 주니어 준비생 현우" (27세)**
- 국비교육/부트캠프를 들었지만 "혼자서 CRUD를 처음부터 끝까지" 못 만든다.
- 복붙은 되는데 구조가 안 보인다. 면접에서 "이 코드 왜 이렇게 짰어요?"에 답을 못 한다.

**서브 페르소나 2 — "사이드 프로젝트가 필요한 직장인 서연" (31세)**
- 비개발 직군 직장인. 자기 아이디어를 직접 MVP로 만들어보고 싶다.
- 시간이 없어서 하루 10~15분, 출퇴근길에 폰으로 조금씩 하고 싶다.

세 명 모두 공통점: **"개념은 나중에. 일단 돌아가는 걸 내 손으로 만들고 싶다."**

## 3. 사용자가 겪는 문제 정의

1. **진입 장벽이 이론에 막혀 있다.** 대부분의 강의가 "백엔드란?", "HTTP란?", "객체지향이란?"으로 시작해서 정작 손은 못 움직인다.
2. **파일 간 연결 감각이 없다.** Controller·Service·Repository·Entity·View가 따로 놀고, "요청이 들어오면 무슨 일이 일어나는지"가 머릿속에 그려지지 않는다.
3. **'복붙은 되는데 응용이 안 된다'.** 강의 그대로 따라 치면 되지만, 글자 하나 바꾸면 무너진다. 왜 그렇게 쓰는지 체득이 안 됐기 때문.
4. **완성 경험이 없다.** 끝까지 만들어 본 적이 없어서 "배포된 내 서비스"라는 성취가 없다. 그래서 동기가 꺾인다.
5. **막혔을 때 물어볼 곳이 없다.** 에러 메시지 한 줄에 몇 시간을 날린다.

## 4. 이 서비스가 해결하는 방식

| 기존 학습 | BackendQuest |
|---|---|
| 이론 → 실습 (이론에서 이탈) | 실습 → (필요할 때만) 이론. 용어 설명은 "왜?" 버튼 뒤에 숨김 |
| 긴 영상 강의 | 10~30초짜리 게임 문제 |
| 파일을 처음부터 타이핑 | 보기 선택 → 드래그 → 빈칸 → 직접입력 5단계로 난이도 상승 |
| 연결 감각을 말로 설명 | "선 긋기/위치 맞추기" 게임으로 연결을 손으로 체득 |
| 완성물 없이 끝 | 레슨을 풀수록 실제 게시판 파일이 한 줄씩 채워지고, 챕터 끝에 배포까지 |
| 막히면 검색 | AI 튜터가 틀린 이유·다음 할 일·에러 해석을 즉시 |

**핵심 철학 3줄**
- 설명하지 말고 **시키고**, 시킨 다음 **짧게** 알려준다.
- 모든 문제는 *진짜 게시판 프로젝트의 한 조각*이다 (버려지는 연습문제 없음).
- "지금 몰라도 되는 것"과 "지금 꼭 알아야 하는 것"을 AI가 구분해 준다.

## 5. MVP 범위

**MVP 한 문장:** "Spring Boot 게시판 CRUD를, 보기 선택부터 직접 코드 작성까지 게임으로 완성하고, 로컬에서 실행해 브라우저로 확인하는 것까지."

**MVP에 포함 (Must)**
- 단계별 학습 맵 (1개 트랙: Spring Boot / 게시판 CRUD)
- 문제 유형 5종: ① 보기 선택 ② 연결하기(선 긋기) ③ 순서 맞추기 ④ 빈칸 채우기 ⑤ 직접 입력
- 게임 요소: XP, 하트(실수 제한), 연속학습(streak), 즉시 정답/오답 피드백
- "왜?" 도움말 버튼 (용어 설명을 접어둠)
- AI 튜터(텍스트): 오답 이유 설명 + 에러 해석 (1차는 규칙기반 힌트 + LLM 보조)
- 레슨을 풀면 실제 프로젝트 파일이 누적되는 "내 프로젝트 뷰"
- 챕터 종료 시 완성 코드 ZIP 다운로드 + 로컬 실행 가이드

**MVP에서 제외 (Later)**
- GitHub/GitLab 자동 연동, AWS 자동 배포 (MVP는 "가이드 + 체크" 수준)
- 멀티 트랙(Node/NestJS/Django/FastAPI)
- 브라우저 내 실시간 코드 실행 샌드박스 (초기엔 정적 채점 + 로컬 실행)
- 소셜/랭킹/리더보드
- 결제/구독

**MVP 성공 기준**
- 신규 사용자의 40% 이상이 챕터 1(프로젝트 생성~첫 목록 조회)을 완주.
- 완주자의 절반 이상이 "처음으로 백엔드 구조가 보였다"고 응답.

## 6. 전체 학습 커리큘럼 (Spring Boot / 게시판 트랙)

전체는 8개 챕터. 각 챕터는 5~8개 레슨, 각 레슨은 4~10개의 짧은 문제로 구성됩니다. 챕터를 끝낼 때마다 게시판의 한 기능이 "실제로 작동"합니다.

```
[0] 워밍업: 길 익히기        → 화면 둘러보기, 첫 정답의 쾌감
[1] 프로젝트 만들기           → 빈 Spring Boot 앱이 실행됨 (포트가 뜸)
[2] 데이터 모양 잡기 (Entity+DB) → posts 테이블이 생기고 데이터 1개가 저장됨
[3] 글 목록 보기 (Read)       → /posts 로 들어가면 글 목록이 보임
[4] 글 쓰기 (Create)          → 글을 작성하면 목록에 추가됨
[5] 글 상세·수정·삭제 (R/U/D)  → 게시판 CRUD 완성
[6] API로도 열기 (REST)       → 같은 기능을 JSON API로 호출
[7] 세상에 내보내기 (배포)     → GitHub push + 무료 클라우드 배포, 운영/에러 확인
```

각 챕터는 **"하나의 작동하는 결과물"** 을 보상으로 줍니다. 챕터 2를 끝내면 "데이터가 저장됐다", 챕터 4를 끝내면 "내가 쓴 글이 보인다" 같은 식입니다.

## 7. 챕터별 목표

**챕터 0 — 길 익히기 (Onboarding)**
- 목표: 문제 푸는 법 체득. "정답을 맞히면 코드가 채워진다"는 규칙 이해.
- 산출물: 없음(튜토리얼). 보상: 첫 streak 시작.

**챕터 1 — 프로젝트 만들기**
- 목표: 프로젝트 폴더 구조의 큰 그림 + 앱을 실행한다는 감각.
- 핵심 감각: "main 함수가 앱을 켠다", "폴더마다 역할이 있다".
- 산출물: 실행되는 빈 Spring Boot 프로젝트 (`localhost:8080`이 응답).

**챕터 2 — 데이터 모양 잡기 (Entity + DB)**
- 목표: "DB에 저장될 데이터의 모양 = Entity" 감각.
- 핵심 감각: "Entity 필드 ↔ DB 컬럼은 짝꿍이다".
- 산출물: `Post` 엔티티 + `posts` 테이블 + 샘플 데이터 1건.

**챕터 3 — 글 목록 보기 (Read)**
- 목표: 요청 → Controller → Service → Repository → DB → 화면의 한 바퀴를 직접 연결.
- 핵심 감각: "주소로 들어오면 Controller가 받는다", "Controller는 Service에게 시킨다".
- 산출물: `/posts` 접속 시 글 목록 화면(`posts/list.html`)이 뜸.

**챕터 4 — 글 쓰기 (Create)**
- 목표: 폼에서 데이터를 받아 DB에 저장하는 POST 흐름.
- 핵심 감각: "GET은 보여주기, POST는 만들기", "폼 입력이 객체로 들어온다".
- 산출물: 글 작성 → 목록에 새 글이 추가됨.

**챕터 5 — 상세·수정·삭제 (Read one / Update / Delete)**
- 목표: id로 한 건을 다루는 흐름 (`/posts/{id}`), PUT/PATCH/DELETE.
- 핵심 감각: "주소 속 {id}가 어떤 글인지 알려준다".
- 산출물: **게시판 CRUD 완성** (목록·상세·작성·수정·삭제 전부 작동).

**챕터 6 — API로도 열기 (REST)**
- 목표: 같은 기능을 화면 대신 JSON으로. View 방식과 API 방식 비교.
- 핵심 감각: "API면 화면 대신 JSON을 준다", "`@Controller` vs `@RestController`".
- 산출물: `/api/posts` 계열 JSON API + Postman/브라우저 테스트.

**챕터 7 — 세상에 내보내기 (배포)**
- 목표: GitHub push → 무료 클라우드(Render/Fly.io) 배포 → 동작 확인 → 에러/로그 보기.
- 핵심 감각: "내 코드가 내 컴퓨터 밖에서도 돈다", "로그는 무슨 일이 있었는지 적힌 일기".
- 산출물: **인터넷 주소로 접속되는 내 게시판** + 간단 운영 시나리오 경험.

## 8. 각 챕터별 대표 퀴즈 예시

각 문제는 1문제당 10~30초. 아래는 챕터별 "대표 1문제"입니다. (실제 첫 레슨의 풀세트는 20장 참고)

**챕터 1 · 위치 맞추기**
> 새 글을 보여주는 화면 파일 `list.html`은 어느 폴더에 둘까요?
> `[ src/main/resources/templates ]` · `[ src/main/resources/static ]` · `[ src/main/java ]`
> 정답: `templates` — 힌트: "서버가 그려서 내려주는 화면(Thymeleaf)은 templates에 살아요."

**챕터 2 · 연결하기 (선 긋기)**
> 왼쪽 Entity 필드와 오른쪽 DB 컬럼을 이어보세요.
> `title` —— `title (VARCHAR)`  /  `createdAt` —— `created_at (TIMESTAMP)`
> 정답: 같은 의미끼리 연결. 힌트: "자바의 createdAt은 DB에서 created_at으로 변신해요."

**챕터 3 · 빈칸 채우기**
> 글 목록 주소를 받는 코드입니다. 빈칸을 채우세요.
> `@GetMapping("____")  public String list(...) { ... }`
> 보기: `/posts` · `/post/list` · `/list`
> 정답: `/posts`

**챕터 3 · 순서 맞추기**
> "글 목록 보기"가 작동하는 순서를 맞추세요.
> `[브라우저가 /posts 요청]` → `[Controller가 받음]` → `[Service에게 목록 요청]` → `[Repository가 DB 조회]` → `[화면에 표시]`

**챕터 4 · 코드 블록 선택**
> 글을 저장하는 함수는 어느 것일까요?
> A) `posts.add(post)`  B) `repository.save(post)`  C) `repository.delete(post)`
> 정답: B — 힌트: "저장은 save, 삭제는 delete."

**챕터 4 · 위치 맞추기**
> `repository.save(post)` 이 코드는 어디에 들어갈까요?
> `[ Controller ]` · `[ Service ]` · `[ Repository 호출은 Service가 ]`
> 정답: Service — 힌트: "Controller는 받기만, 실제 일은 Service가 시켜요."

**챕터 5 · 직접 입력**
> id로 글 하나를 받는 주소를 완성하세요: `@GetMapping("/posts/____")`
> 정답: `{id}`

**챕터 5 · HTTP Method 고르기**
> 글 삭제에 가장 어울리는 방식은?
> `GET` · `POST` · `PUT` · `DELETE` → 정답: `DELETE`

**챕터 6 · 위치/개념**
> 화면 대신 JSON을 주려면 클래스 위에 무엇을 붙일까요?
> `@Controller` · `@RestController` → 정답: `@RestController`

**챕터 7 · 순서 맞추기 (배포)**
> 배포 순서를 맞추세요.
> `[코드 커밋]` → `[GitHub에 push]` → `[클라우드가 코드 가져감]` → `[빌드]` → `[실행/공개 주소]`

**챕터 7 · 디버깅**
> 화면이 안 뜨고 `Whitelabel Error Page 404`가 떴어요. 가장 가능성 높은 원인은?
> A) DB가 비었다  B) Controller의 주소(`@GetMapping`)와 입력한 URL이 다르다  C) 인터넷이 끊겼다
> 정답: B — 힌트: "404 = 그 주소를 받아줄 Controller가 없다는 뜻."

## 9. 실제 CRUD 서비스가 완성되는 단계별 흐름

레슨을 풀 때마다 **버려지지 않고** 같은 게시판 프로젝트에 코드가 누적됩니다. 누적되는 실제 파일들:

```
board/
├─ src/main/java/com/example/board/
│  ├─ BoardApplication.java          ← 챕터1: 앱을 켜는 시작점
│  ├─ post/
│  │  ├─ Post.java                   ← 챕터2: 데이터 모양(Entity)
│  │  ├─ PostRepository.java         ← 챕터3: DB와 대화하는 창구
│  │  ├─ PostService.java            ← 챕터3~5: 실제 처리 흐름
│  │  ├─ PostController.java         ← 챕터3~5: 화면용(주소를 받음)
│  │  └─ PostApiController.java      ← 챕터6: JSON API용
├─ src/main/resources/
│  ├─ templates/posts/
│  │  ├─ list.html                   ← 챕터3: 목록 화면
│  │  ├─ detail.html                 ← 챕터5: 상세 화면
│  │  └─ form.html                   ← 챕터4~5: 작성/수정 폼
│  └─ application.yml                ← 챕터2: DB 설정
└─ build.gradle                      ← 챕터1: 사용할 도구 목록
```

**기능별 "완성됨" 체크포인트 (사용자가 눈으로 확인하는 것)**

| 단계 | 사용자가 확인하는 것 | 작동하는 기능 |
|---|---|---|
| 챕터1 끝 | 브라우저에 "앱이 켜졌다" | 서버 실행 (`localhost:8080`) |
| 챕터2 끝 | H2 콘솔에 `posts` 표 + 데이터 1줄 | DB 저장 확인 |
| 챕터3 끝 | `/posts` 에 글 목록 표시 | **Read(목록)** |
| 챕터4 끝 | "글쓰기" 후 목록에 새 글 | **Create** |
| 챕터5 끝 | 글 클릭→상세, 수정/삭제 버튼 작동 | **Read(상세)/Update/Delete = CRUD 완성** |
| 챕터6 끝 | `/api/posts` 가 JSON 반환 | **REST API** |
| 챕터7 끝 | 친구에게 보낼 수 있는 인터넷 주소 | **배포/운영** |

## 11. 문제 유형별 UX 설명

| 유형 | 인터랙션 | 난이도 | 대표 문제 | UX 포인트 |
|---|---|---|---|---|
| **A. 연결하기** | 왼쪽 점 → 오른쪽 점 선 긋기(드래그) | L1~L2 | Controller 함수 ↔ URL ↔ View | 맞으면 선이 초록으로 굳고 ✨, 틀리면 선이 튕겨 나감 |
| **B. 위치 맞추기** | 코드 블록을 3개 영역 중 하나로 탭/드롭 | L1~L2 | "이 코드는 Controller? Service? Repository?" | 영역에 올리면 미리보기 음영, 정답 영역이 잠깐 빛남 |
| **C. 순서 맞추기** | 카드들을 위아래로 드래그 정렬 | L2 | 요청→Controller→Service→Repo→DB→응답 | 흐름선이 위에서 아래로 흐르는 애니메이션 |
| **D. 코드 블록 선택** | 보기 중 탭 1번 | L1 | "저장 함수는 save? delete?" | 가장 빠른 문제(10초). 워밍업용 |
| **E. 빈칸 채우기** | 보기 탭 또는 키보드 입력 | L3 | `@GetMapping("____")` | 보기 제공→점차 보기 제거(입력 전환) |
| **F. 직접 입력** | 코드 에디터(자동완성·괄호도움) | L4 | "삭제 API를 직접 작성" | 부분 정답도 인정, 실시간 문법 힌트 |
| **G. 디버깅** | 에러 화면 보고 원인 선택→수정 | L4 | "404가 떴다. 원인은?" | 진짜 에러 메시지를 보여주고 "범인 찾기" 게임화 |

**난이도 상승 규칙 (한 기능을 여러 번 다른 방식으로 반복)**
- 같은 "글 목록 조회" 개념을 → 챕터3에선 보기 선택(L1)으로, 복습에선 빈칸(L3), 챕터 후반엔 직접 입력(L4)으로 재출제. 반복하되 매번 난이도를 올려 체득시킵니다.

## 12. 정답 판정 방식

문제 유형마다 채점기를 다르게 둡니다. 핵심은 **"엄격하게 틀렸다 하지 말고, 의도가 맞으면 인정"** 입니다.

**1) 선택형 / 연결 / 순서 / 위치 (A~E 보기형)**
- 정해진 정답 키와 단순 비교. 즉시 판정. (서버 왕복 없이 클라이언트에서 채점 가능 → 빠름)

**2) 빈칸·직접 입력 (E 입력 / F)**
- **정규화 후 비교**: 공백/따옴표(`"` vs `'`)/세미콜론 유무/대소문자(키워드 한정) 차이는 무시.
  - 예: `@GetMapping("/posts")` 와 `@GetMapping( '/posts' )` 는 같은 정답으로 인정.
- **AST(구문 트리) 기반 비교 (F 고난도)**: 변수명이 달라도 구조가 같으면 정답.
  - 예: 정답이 `model.addAttribute("posts", list)` 인데 사용자가 `list` 대신 `postList`로 썼다 → 변수명 차이는 통과, 단 의미가 깨지면 오답.
- **다중 정답 허용**: `findAll()` 결과를 `List`로 받든 `var`로 받든 인정.

**3) 직접 작성 코드 (F) — 단계적 채점**
- ① 컴파일/문법 검사 → ② 정답 패턴(필수 토큰: `@PostMapping`, `save`, `redirect:`) 포함 검사 → ③ (서버 샌드박스가 붙는 후속 버전) 실제 실행 후 기대 결과(HTTP 200 + 리다이렉트) 검증.
- 부분 점수: 필수 토큰 일부만 맞으면 "거의 다 왔어요" 피드백 + 어느 부분이 빠졌는지 표시.

**4) 디버깅 (G)**
- "원인 선택"은 선택형 채점. "수정"은 입력형 채점.
- 틀린 코드 → 올바른 코드로의 diff가 정답 패턴과 일치하는지 검사.

**오답 피드백 원칙**: 정답을 바로 보여주지 않고, *한 칸짜리 힌트*를 먼저 → 2회 틀리면 정답 + AI 설명 제안.

## 13. AI 튜터 기능 설계

AI 튜터는 "선생님"이 아니라 **"옆에서 같이 보는 짝꿍"** 컨셉. 긴 강의 금지, 항상 3~4줄 이내.

**핵심 기능 6가지**
1. **틀린 이유를 쉽게** — "이 함수는 `/posts`로 들어와야 하는데, `/list`라고 적었어요. 주소(@GetMapping)와 실제 접속 주소가 같아야 Controller가 받아요."
2. **지금 코드의 연결 설명** — "방금 쓴 `service.findAll()`은 → `PostService`로 가고 → 거기서 `repository.findAll()`을 불러 → DB에서 글을 다 가져와요." (파일 흐름을 화살표로)
3. **내가 쓴 코드 피드백** — 직접 입력 문제에서 "동작은 하는데, 보통은 `posts`라는 이름으로 넘겨요(화면 파일이 그 이름을 기대하거든요)."
4. **에러 메시지 해석** — `Whitelabel Error Page 404` → "주소를 받아줄 Controller가 없다는 뜻. @GetMapping 주소를 확인해요." / `Table "POSTS" not found` → "테이블이 아직 안 만들어졌어요. 챕터2의 Entity를 확인."
5. **다음에 뭘 할지 안내** — "목록은 됐으니, 이제 '글쓰기(POST)'로 넘어가요. 폼에서 받은 데이터를 save 하는 차례예요."
6. **'지금 몰라도 됨 / 꼭 알아야 함' 구분** — "트랜잭션은 지금 몰라도 돼요(나중에). 지금 꼭 알 건 'save가 저장한다'는 것 하나예요."

**후속(확장) 기능**
- 사용자의 GitHub/GitLab repo를 읽어 "지금 챕터4까지 했네요. Update 기능이 비어 있어요" 진단.
- 사용자가 만든 코드에 맞춰 다음 문제를 동적 생성(예: 사용자가 필드에 `author`를 추가했다면 그 필드로 빈칸 문제 출제).

**구현 방식 (비용/속도 고려)**
- **1차(MVP)**: 대부분의 힌트는 **규칙기반(미리 작성된 힌트 템플릿)** 으로 즉시·무료 제공. 사용자가 "💬 AI에게 물어보기"를 누를 때만 LLM 호출.
- LLM 호출 시 컨텍스트로 (현재 레슨, 정답, 사용자가 제출한 코드, 발생한 에러)를 함께 전달 → 정확하고 짧은 답.
- 안전장치: 답을 그냥 떠먹여 주지 않도록 "힌트 우선" 프롬프트. 3회 이상 막히면 정답 공개.

## 14. GitHub / GitLab / AWS 연동 구조

처음부터 복잡하게 만들 필요는 없지만, 구조상 확장 가능하게 설계합니다. 단계별로 켭니다.

**레벨 0 (MVP) — "가이드 + 수동 체크"**
- 챕터7에서 사용자가 직접 GitHub 계정을 만들고, 우리가 주는 명령어를 복사-붙여넣기.
- 우리 서버는 "사용자가 입력한 repo URL"을 받아 **공개 API로 존재 여부만 확인**(`GET https://api.github.com/repos/{user}/{repo}`)하고 ✅ 체크.
- 배포도 마찬가지로 Render/Fly.io 가이드 + "공개 주소 입력 → 우리가 접속해서 200이면 통과".

**레벨 1 — OAuth 연동(읽기)**
- 사용자가 "GitHub 연결" 버튼 → OAuth 로그인 → 우리가 repo 목록/커밋/파일을 **읽기 전용**으로 접근.
- AI 튜터가 repo를 읽어 진행 상태 진단(13장 확장 기능).
- 토큰은 암호화 저장, 최소 scope(`repo:status`, `read:user`)만 요청.

**레벨 2 — 배포 파이프라인 연동**
- GitHub Actions 워크플로 템플릿(`.github/workflows/deploy.yml`)을 우리가 생성해 push → Render/Fly.io/AWS로 자동 배포.
- AWS는 입문자에겐 어려우므로 **기본은 Render/Fly.io, AWS는 "고급" 선택지**로.
- 배포 로그/에러 로그를 우리 화면에 스트리밍해서 "운영 화면"을 게임 안에서 경험.

**연동 아키텍처 개요**
```
[사용자] ──OAuth──> [BackendQuest 서버] ──(GitHub/GitLab API)──> [사용자 repo]
                          │
                          ├──(Render/Fly.io API)──> [배포 환경] ──> 공개 URL
                          └──(webhook 수신)──> 배포 상태/로그를 학습 화면에 표시
```

연동은 모두 **플러그인식(어댑터 패턴)**: `GitProvider` 인터페이스(구현체: GitHub/GitLab), `DeployProvider` 인터페이스(구현체: Render/Fly.io/AWS). 새 제공자 추가가 쉬움.

## 15. 데이터베이스 설계 초안

두 종류의 DB가 있습니다: ① **학습 플랫폼 자체의 DB**(사용자·진도·문제), ② **사용자가 만드는 게시판의 DB**(학습 산출물, `posts`).

**① 플랫폼 DB (PostgreSQL)**

```
users
  id (PK), email, nickname, password_hash, created_at, last_active_at

tracks                         -- 예: "Spring Boot 게시판"
  id (PK), slug, title, description, order

chapters
  id (PK), track_id (FK), title, order, reward_desc

lessons
  id (PK), chapter_id (FK), title, order, est_minutes

problems                       -- 개별 문제
  id (PK), lesson_id (FK), type(enum: SELECT/CONNECT/ORDER/PLACE/FILL/WRITE/DEBUG),
  prompt, payload(JSON), answer_key(JSON), hint, why_explain, order

user_progress                  -- 사용자별 진도
  id (PK), user_id (FK), lesson_id (FK), status(locked/current/done),
  completed_at

problem_attempts               -- 문제별 시도 기록 (분석/AI용)
  id (PK), user_id (FK), problem_id (FK), submitted(JSON), is_correct,
  attempt_count, created_at

user_stats                     -- 게임 상태
  user_id (PK), xp, hearts, streak_days, last_streak_date

user_projects                  -- 사용자가 누적 중인 게시판 코드
  id (PK), user_id (FK), track_id (FK), files(JSON: 파일경로→내용), updated_at

integrations                   -- 외부 연동
  id (PK), user_id (FK), provider(github/gitlab/render/aws),
  access_token(encrypted), repo_url, deploy_url, status
```

**② 사용자가 만드는 게시판 DB (학습 산출물 — 챕터2에서 사용자가 직접 설계)**

```
posts
  id          BIGINT       PK, auto increment
  title       VARCHAR(200) NOT NULL       -- 제목
  content     TEXT                         -- 내용
  author      VARCHAR(50)                  -- 작성자
  created_at  TIMESTAMP    DEFAULT now()   -- 작성일
  updated_at  TIMESTAMP                    -- 수정일
```

`posts` 테이블은 사용자가 "Entity 필드 ↔ DB 컬럼 연결하기" 게임을 풀면서 스스로 만들어 가는 것이 핵심입니다. MVP에서는 H2(파일/인메모리)로 시작 → 배포 단계에서 PostgreSQL로 전환하는 경험까지 제공.

```

- **채점 샌드박스**: MVP는 정적 채점(패턴/AST)만. 후속 버전에서 Docker로 격리된 실제 실행(직접 작성 코드를 진짜 돌려봄)을 추가.
- **확장성**: 문제는 전부 데이터(JSON payload)로 정의 → 새 트랙(Node/Django)을 코드 수정 없이 "문제 데이터 추가"만으로 확장.
- **AI 비용 관리**: 규칙기반 1차 필터로 LLM 호출을 최소화.

**문제 1 — (유형 D, 코드 블록 선택) · 10초**

### (B) "게시글 작성" 기능 — 실제 파일명과 코드로 보는 연결 흐름

> 사용자가 챕터 4를 풀면 **이 코드들이 실제로 자기 프로젝트에 만들어집니다.** 아래는 "글쓰기" 버튼 한 번이 어떤 파일들을 거쳐 DB에 저장되고 다시 화면으로 돌아오는지를, 진짜 파일명과 함께 정리한 것입니다. (이게 곧 챕터 4 레슨들의 정답 모음입니다.)

**한눈에 보는 연결 지도**
```
[브라우저: 글쓰기 폼 작성 후 '저장' 클릭]
        │  POST /posts  (제목, 내용, 작성자)
        ▼
PostController.java   create(PostForm form)        ← 카운터: 요청을 받음
        │  postService.save(form)
        ▼
PostService.java      save(PostForm form)           ← 처리 담당: 폼을 Post로 변환
        │  postRepository.save(post)
        ▼
PostRepository.java   save(post)  (JPA가 제공)       ← DB와 대화
        │  INSERT INTO posts ...
        ▼
posts 테이블 (DB)     새 글 1줄 저장됨
        │
        ▼
PostController.java   return "redirect:/posts"       ← 목록으로 돌려보냄
        ▼
[브라우저: /posts 글 목록에 방금 쓴 글이 보임]
```

각 파일을 실제 코드로 보면:

**① `src/main/java/com/example/board/post/Post.java` — 데이터 모양 (Entity)**
```java
@Entity
@Table(name = "posts")          // ← DB의 posts 테이블과 짝꿍
public class Post {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;       // ← posts.title 컬럼
    private String content;     // ← posts.content 컬럼
    private String author;      // ← posts.author 컬럼

    @CreationTimestamp
    private LocalDateTime createdAt;   // ← posts.created_at 컬럼
    // getter/setter 생략
}
```

**② `src/main/java/com/example/board/post/PostForm.java` — 폼에서 받는 데이터 모양**
```java
public class PostForm {         // 화면(form.html)이 보내는 입력값을 담는 그릇
    private String title;
    private String content;
    private String author;
    // getter/setter 생략
}
```

**③ `src/main/resources/templates/posts/form.html` — 글쓰기 화면 (View)**
```html
<!-- 사용자가 글을 입력하는 폼. action 주소와 method가 핵심! -->
<form action="/posts" method="post">
    <input type="text" name="title"   placeholder="제목">
    <textarea       name="content" placeholder="내용"></textarea>
    <input type="text" name="author"  placeholder="작성자">
    <button type="submit">저장</button>
</form>
```
> 연결 포인트: `action="/posts"` + `method="post"` → 아래 Controller의 `@PostMapping("/posts")`로 들어갑니다. 이름(`name="title"`)이 `PostForm`의 필드명과 같아야 자동으로 담깁니다.

**④ `src/main/java/com/example/board/post/PostController.java` — 화면용 컨트롤러**
```java
@Controller
public class PostController {

    private final PostService postService;
    public PostController(PostService postService) {   // Service를 주입받음
        this.postService = postService;
    }

    // (a) 글쓰기 폼 화면 보여주기 — GET
    @GetMapping("/posts/new")
    public String newForm() {
        return "posts/form";          // → templates/posts/form.html
    }

    // (b) 폼이 보낸 데이터로 글 저장하기 — POST
    @PostMapping("/posts")
    public String create(PostForm form) {
        postService.save(form);       // 실제 일은 Service에게 시킴
        return "redirect:/posts";     // 저장 후 목록으로 이동
    }

    // (c) 글 목록 보기 — GET (챕터3에서 만든 것)
    @GetMapping("/posts")
    public String list(Model model) {
        model.addAttribute("posts", postService.findAll());
        return "posts/list";          // → templates/posts/list.html
    }
}
```

**⑤ `src/main/java/com/example/board/post/PostService.java` — 처리 흐름 담당**
```java
@Service
public class PostService {

    private final PostRepository postRepository;
    public PostService(PostRepository postRepository) {
        this.postRepository = postRepository;
    }

    public void save(PostForm form) {
        Post post = new Post();                 // 폼 데이터를 Entity로 변환
        post.setTitle(form.getTitle());
        post.setContent(form.getContent());
        post.setAuthor(form.getAuthor());
        postRepository.save(post);              // DB에 저장하라고 Repository에 시킴
    }

    public List<Post> findAll() {
        return postRepository.findAll();        // DB에서 전부 가져오기
    }

    // (API용) 저장한 뒤 만들어진 글을 그대로 돌려줌
    public Post saveAndReturn(PostForm form) {
        Post post = new Post();
        post.setTitle(form.getTitle());
        post.setContent(form.getContent());
        post.setAuthor(form.getAuthor());
        return postRepository.save(post);       // save()는 저장된 Post를 반환
    }
}
```

**⑥ `src/main/java/com/example/board/post/PostRepository.java` — DB와 대화하는 창구**
```java
public interface PostRepository extends JpaRepository<Post, Long> {
    // save(), findAll(), findById(), delete() 등을 JPA가 자동으로 제공!
    // 우리는 한 줄도 안 써도 INSERT/SELECT가 됩니다.
}
```

**연결 요약 (사용자가 이 기능 하나로 체득하는 감각)**
- `form.html`의 `action="/posts" method="post"` → `PostController.create()`의 `@PostMapping("/posts")` 와 **짝꿍**.
- Controller는 받기만 하고 → `PostService.save()`에게 **시킴**.
- Service는 폼을 Post로 바꿔서 → `PostRepository.save()`로 **DB에 저장**.
- 저장 끝나면 `return "redirect:/posts"` → 다시 `list()`가 실행되어 **목록에 새 글이 보임**.
- "하나의 기능(글쓰기)은 form.html · Controller · Service · Repository · Entity 5개 파일이 연결되어 완성된다" — 이게 핵심 감각.

**(참고) 같은 기능의 API 버전 — 챕터 6에서 비교**
`src/main/java/com/example/board/post/PostApiController.java`
```java
@RestController                            // ← 화면 대신 JSON을 돌려줌
@RequestMapping("/api/posts")
public class PostApiController {

    private final PostService postService;
    public PostApiController(PostService postService) {
        this.postService = postService;
    }

    @PostMapping                            // POST /api/posts
    public Post create(@RequestBody PostForm form) {
        return postService.saveAndReturn(form);   // 저장한 글을 JSON으로 반환
    }

    @GetMapping                             // GET /api/posts
    public List<Post> list() {
        return postService.findAll();        // 글 목록을 JSON 배열로
    }
}
```
> 사용자는 여기서 "`@Controller`는 화면(form.html)을, `@RestController`는 JSON을 준다"는 차이를 위치 맞추기 문제로 체득합니다. Service·Repository는 **그대로 재사용** — "화면이든 API든 처리 로직은 같다"는 걸 보여줍니다.

## 부록: 톤 & 절대 금지 원칙 (제작 가이드)

콘텐츠를 만드는 모든 사람이 지킬 규칙:
- ❌ "백엔드란 무엇인가"로 시작하지 않는다. ✅ "글 목록을 띄워봅시다"로 시작한다.
- ❌ 용어를 앞에 길게 설명하지 않는다. ✅ "왜?" 버튼 뒤에 3줄로 숨긴다.
- ❌ CS 이론 강의가 되지 않는다. ✅ 모든 문제는 진짜 게시판의 한 조각이다.
- ❌ 버려지는 연습문제를 만들지 않는다. ✅ 푼 결과가 내 프로젝트 파일로 쌓인다.
- ❌ 영상만 보는 서비스가 아니다. ✅ 손으로 클릭/연결/입력하며 완성한다.
- ✅ 끝에는 반드시 "작동하는 게시판 + 인터넷 주소"가 남는다.
